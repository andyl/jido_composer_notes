Composer Ease of Use

Is Composer too much to learn, and how would we know?

October 2026 · Andy Leak · Copyright © 2026 by Andy Leak - All Rights Reserved

The concern

A core concern for Composer is that it will be too complex for end-users to understand and learn.

  • Composer would be another thing to learn, more tooling to maintain, more things to maintain, monitor, debug.
  • By introducing a new framework, we violate the maxim: "the best part is no part, the best code is no code".
  • Probably it is OK to violate this maxim if the productivity benefits are very high, and the learning curve is very low.

Three end-user profiles

When we think about improving the usability of Composer, we want to keep three profiles in mind:

The NeophyteA non-technical user who will use Composer through a web interface or an LLM chat to build applications.
The CasualDevAn Elixir developer who wants to build a new application.
The SuperDevA hardcore Cookbook maintainer. Maybe one SuperDev for every 100 CasualDevs.

Self-assessment

  • The usability outlook for building applications with Composer is good.
  • But there is a big overhead for developers to build and test cookbooks. Ease-of-use for Cookbook development and maintenance is a big red flag.

Usability steps already taken

  • Simplification of terminology and usage model
  • Bash completions for composer mix tasks
  • Linting for recipe files
  • LSP for recipe files
  • 1st level documentation, built-in guides
  • Envision a graphic "menu" structure for end-users

Questions

  • What can we do to improve Composer usability, especially for Cookbook development and maintenance? Earlier we talked about the notion of exploratory building. My gut tells me that this would be a good avenue to explore.
  • How can we benchmark ease-of-use?
    • Neophyte: productivity improvement will probably be infinite. Not possible to build apps before Composer. (But what about a Neophyte with just an LLM?)
    • CasualDev: maybe compare build times using Composer to build time following blog instructions.
    • SuperDev: Cookbook development is overhead. Maybe measure team productivity?
  • Specifically: how can we measure ease-of-use, and graph our performance over time?

1Are the concerns valid?

Analysis dated 2026-10-21, based on composer and composer_lab as of this date (guides/cookbooks.md, Mix.Tasks.Composer.New, the step tests under composer_lab/test/). Related: 261020_StepWiseCommits.md, 261021_LlmBenchmarks.md.

Partly. The "no part" maxim costs less than it seems for app builders, and more than it seems for cookbook maintainers.

  • Composer is a dev-only dependency. The generated app is plain Phoenix / Ash code; the cookbook module is guarded with Code.ensure_loaded?, so the app compiles without Composer. Nothing to monitor or debug in production. That's a strong answer to "more tooling to maintain", and it should be said up front in the docs: Composer leaves no trace in your app.
  • The CasualDev's learning cost is small. About three commands (composer.new, recipe.run, recipe.edit) and four nouns (cookbook, recipe, step, template). The terminology work has paid off here.
  • The Neophyte never sees Composer at all, if the web/chat front end works. Their ease of use is the front end's problem, plus one thing Composer owns: does the recipe produce a working app?
  • The SuperDev concern is real, and it's the important one. The 1:100 ratio is the leverage argument for Composer: one maintainer's effort serves a hundred app builders. But that only holds if cookbooks stay green. If they rot, every CasualDev and Neophyte inherits the breakage, and the "outlook is good" for app building goes with it.
Key point

The two outlooks are not independent: app-building ease-of-use is downstream of cookbook health.

2Where the SuperDev's overhead comes from

"Cookbook development is hard" breaks down into five separate costs. They need different fixes:

CostWhat it isAddressed today?
AuthoringWriting Igniter code. Igniter's API, not Composer's, is the curve.Partly: generators, LSP, lint
Feedback latencyEdit step → new app → deps fetch → compile → try it. Minutes.No
VerificationStep tests check the diff (assert_creates), not the result.Unit level only
CombinatoricsSteps × recipes × flags × host-app states interact.requires/provides/conflicts warn
Upstream driftPhoenix, Ash, installers and CSS libraries change under you.Ad hoc (daisy_ui_drift_test.exs)

The usability work so far (completions, lint, LSP, guides, terminology) is all on the authoring row: it helps you write a recipe file correctly. Nothing yet shortens the loop from "I changed a step" to "the app it generates compiles, passes its tests and boots." That gap is the red flag, and the gut feeling about exploratory building points straight at it.

3Strategies

1. Make the inner loop fast: exploratory building as a command

Something like:

$ mix composer.try composer_lab:lv/base            # scratch app, run, check, report
$ mix composer.try composer_lab:lv/base --keep     # leave the app for poking at
  • Build into a scratch directory, from a cached base snapshot (the phx.new output with deps already fetched and compiled), so a warm run takes seconds instead of minutes. Caching is what makes this usable.
  • After the run, apply a fixed set of checks: compile --warnings-as-errors, mix test, mix format --check-formatted, boot and get a 200 from /.
  • Report per step, using step commits from 261020_StepWiseCommits.md, so a failure names the step (git bisect run underneath).
  • This loop is also exactly what an LLM agent needs to maintain a cookbook without a human watching.

2. Recipe-level "golden app" tests

Promote the composer.try checks to a test kind a cookbook can declare:

# test/composer/composer_lab/recipes/lv_test.exs
use Composer.RecipeCase, recipe: "composer_lab:lv/base", checks: [:compile, :test, :boot]

Run them nightly in CI against the latest upstream versions, not the locked ones. That turns upstream drift from a surprise into a red badge the morning after, which is the single biggest maintenance win available.

3. Lower the Igniter barrier

Many steps are "copy these templates, add this config, add this child to the supervision tree." Options:

  • Record a step from a diff. Make the change by hand in a real app, then mix composer.gen.step astral/nav2 --from-diff HEAD~1. Composer writes the templates and a step skeleton; the SuperDev fixes up what can't be inferred.
  • Declarative steps for the common cases (templates + config + deps), with Igniter code only when needed. Fewer lines of code means less to maintain.

4. An LLM skill for cookbook work

As 261001_Overview.md already envisions: ship usage_rules for cookbooks, plus a skill that knows the composer.try loop. The LLM writes and repairs steps; the SuperDev reviews. This changes the SuperDev's job from writing to reviewing, which is the biggest possible reduction in overhead, and it depends on strategies 1 and 2.

5. Keep a surface-area budget

Every new facet, option, mix task and config key is something to learn. Count them (see metrics below) and make each addition justify itself. The original concern is really about this number growing faster than the value.

4Measuring ease of use

Split the metrics in two:

Automated metrics

Run in CI on every release (or nightly). Cheap, repeatable and easy to graph over time. These are the backbone.

Human trials

Occasional, small and expensive. They calibrate the automated metrics and find problems no metric anticipates.

Automated metrics, by persona

PersonaMetricHow
AllRecipe health% of published recipes whose golden app passes all checks on latest upstream
SuperDevInner-loop timeWall clock of a warm composer.try on a reference recipe
SuperDevTime to repairDays from a recipe going red to green again
SuperDevStep costMedian LOC per step; % of steps that are declarative / template-only
SuperDevError quality% of a curated "mistake corpus" that lint/LSP/compile errors catch and name the fix for
CasualDevTime to first appScripted wall clock and command count from empty dir to a green app with a reference feature set
CasualDevSurface areaCount of mix tasks, options, facets, config keys, error types
NeophyteAgent task successA pinned LLM model with a fixed budget runs a fixed task list; record success rate, turns, tokens, time

The mistake corpus is worth a note: a directory of known-wrong recipe files and steps (misspelled ref, use cycle, bare .ex template, step listed before its requires). Each one records the error message it should produce. It doubles as a regression suite for error messages.

Agent task success

This is the most interesting metric, because one harness serves all three personas:

  • Neophyte proxy: "build an app with auth, background jobs and a dashboard."
  • CasualDev proxy: same task, but the agent may read and edit the generated code.
  • SuperDev proxy: "add a step for X to composer_lab", "fix the recipe that broke after the Phoenix upgrade."

Run each task with and without Composer available. That gives the comparison 261021_LlmBenchmarks.md asks for, and answers the parenthetical question: "but what about a Neophyte with just an LLM?" The Neophyte's improvement isn't infinite; the baseline is an LLM alone. Measure the quality of the result too (tests pass, credo, sobelow, boots), not just "an app exists."

Caveat: pin the model version, and re-baseline when you change it, or the graph measures the model instead of Composer.

Human trials

  • CasualDev: the blog-post comparison is the right idea; make it a fixed task list (Phoenix + auth + Oban + Tailwind/daisyUI + deploy config), timed, Composer vs. following the published guides. Record time to a green app and defects found afterward.
  • SuperDev: give a developer who has never written a step a task ("write a step that adds X"), with only the guides. Time it, and note every point where they get stuck. Five people per persona finds most of the problems.
  • A short SUS questionnaire (System Usability Scale, 10 questions) after each trial gives a number comparable across releases.
  • Maintenance log: the SuperDev records hours spent keeping cookbooks green each month. With usage numbers this gives leverage:
leverage = (apps generated × time saved per app) / maintenance hours
Test

If leverage isn't well above 1, the "no part" maxim wins.

Graphing over time

  • The harness writes one JSON line per metric per run: date, composer version, upstream versions, metric, value.
  • Commit the results file, and plot it: a static page on composer_web would do, or a dashboard artifact.
  • Mark releases and upstream upgrades on the x-axis, so a drop can be tied to its cause.

5Recommendation

Start with three metrics, all automated and all served by the same work:

  1. Recipe health (needs golden-app tests, strategy 2)
  2. Inner-loop time (needs composer.try, strategy 1)
  3. Agent task success (needs the harness, and reuses 1 and 2)
Next step

Building composer.try is the highest-value next step: it's the exploratory building loop, it's the measurement harness, and it's the prerequisite for an LLM maintaining cookbooks. That makes it a good candidate to promote to a design.

6Open questions

Harness location

  • Where does the benchmark harness live? composer_lab (it already has the cookbook to test), a new repo, or composer itself?

Reference recipes

  • The metrics need a small, stable set that represents real use, and the set must not change often. Which recipes?

CI cost

  • Golden-app tests against latest upstream are slow. Nightly only? How many recipes?

Ownership

  • Who owns a red recipe in third-party cookbooks? Recipe health on composable.tech could be shown to buyers as a badge, which is also an incentive for cookbook authors.
