1What is Composer?

In one sentence: Composer turns a fresh Elixir app into a working prototype by running a named, shareable list of Igniter changes.

Why Composer was developed

  • Elixir frameworks ship good generators (phx.new) and Igniter installers.
  • Even so, getting from a generated skeleton to a first working prototype takes a lot of manual work, and teams repeat the same work on every new app.
  • That knowledge (which defaults to remove, which packages to add, how to wire them) lives in blog posts, READMEs and people's heads. It isn't in code.

The problems Composer solves

  • Removing generator defaults you don't want.
  • Adding layouts, styles, pages and navigation.
  • Creating seed data.
  • Configuring add-on packages: auth, mailers, API extensions, job queues.
  • Making all of the above repeatable, composable and shareable.

How Composer extends Igniter

  • Igniter provides safe, composable code changes: AST-aware edits shown as one diff before they are applied.
  • Composer adds a layer on top:
    • Metadata on each change (summary, facets, tags, requirements), so humans and agents can search for it and discover it.
    • Composition: ordered lists of changes, switched on and off with flags.
    • Distribution: changes packaged and shipped like any Hex dependency.
  • Any Hex package's own Igniter installer can be used as a step ("hex:oban"), so Composer reuses what the ecosystem already has.

Inspiration: the Ash installer

  • The Ash HQ installer lets you pick features and get a single command that builds the app.
  • Composer generalises that idea. Any framework, team or developer can publish the building blocks, not only one framework's maintainers.

The Composer model: cookbooks, recipes, steps

TermWhat it isAddress
stepone reusable change to the target app (eg an Igniter task)cookbook:step
recipean ordered, flag-aware list of steps; may include other recipescookbook:group/recipe
cookbooka package's bundle of steps, recipes and templatesthe package's OTP app name

A recipe is plain data:

[
  default: [
    shortdoc: "My app's setup",
    flags: [oban: "Add Oban"],
    steps: [
      "core:phx/remove_daisy_ui",      # undo a phx.new default
      "core:setup/credo",              # add a package
      "hex:ash",                       # a Hex package's own installer
      {"hex:oban", if: :oban},         # optional, behind --oban
      "my_app:deploy_config",          # the team's own step
      {:use, "local:dev/tools"}        # include another recipe
    ]
  ]
]
$ mix composer.recipe.run app/default --oban

Where cookbooks live (the same model as Mix tasks)

  • Any dependency that contains lib/composer/<app>.ex is a cookbook. Composer discovers it automatically, the way Mix discovers tasks in deps.
  • core is built into Composer.
  • local holds a developer's personal recipes (~/.config/composer/recipes/*.exs).
  • The app you're working on can be its own cookbook (mix composer.new).

Who writes cookbooks

  • The Composer project: core, plus experimental cookbooks (composer_lab).
  • Framework maintainers: a framework ships a cookbook next to its code, or as a companion package (for example composer_ash or composer_jido).
  • Development teams: house recipes that encode "how we start an app here".

Cookbooks for major Elixir frameworks

  • We envision a cookbook for each major Elixir framework.
  • We intend to prototype cookbooks for:
    • Astral: static sites
    • Francis: small Plug/Bandit web apps
    • Phoenix: web apps and LiveView
    • TermUI: terminal user interfaces
    • Ash: declarative application framework
    • Jido: multi-agent systems
    • Mob: native mobile apps on the BEAM

Current status and links

  • Version 0.2.0, open source.
  • Source: github.com/elixir-composer/composer
  • Experimental cookbook: github.com/andyl/composer_lab (still private)
  • Site: elixir-composer.dev (not yet public)
  • Working today: discovery, recipe/step list/show/run/edit, scaffolding, lint, shell completion, and a language server for recipe files.
  • Not built yet: the web dashboard shown in section 3.
Hypothesis 1

Setting up a new Elixir app is a repeated cost that framework maintainers and teams would rather capture as code. Composer can be explained in a few minutes.

2Our understanding of Jido

This is our outside read. Please correct it.

What we take Jido to be

  • "A runtime for reliable multi-agent systems built on Elixir/OTP for fault isolation, concurrency, and production uptime." (jido.run)
  • Agents hold immutable state and run validated actions. Signals are routed to actions. Directives (emit, schedule) request side effects. Plugins add state and routes.
  • jido_ai adds LLM reasoning, skills and multi-agent orchestration. Runic adds workflows: research, delegation, structured branching.

Why Jido? Our hypothesis, by way of Carl Hewitt

  • Hewitt created the Actor Model. Erlang/OTP processes are actors in practice, so Jido sits on a substrate that Hewitt's ideas describe directly.
  • At Code Mesh LDN 2018, Hewitt himself pointed to Erlang and Elixir as the tactics for building scalable, robust intelligent systems.
  • In Open Systems (1984), Hewitt argued that the following properties belong together and depend on each other:
    • continuous growth
    • no bottlenecks
    • arm's-length relationships between parts
    • inconsistency among knowledge bases
    • decentralized decision-making
    • negotiation among parts
  • Those properties line up with what we think could make agent systems different from ordinary applications:
What agent systems might doHewitt's open-systems property
Operate in a public mesh, not inside one appcontinuous growth; no bottlenecks
Interact in ways the original author did not anticipateinconsistency robustness
Interact with agents by other authors, without pre-planningarm's-length relationships
Evolve over time (how? to what purpose?)continuous growth
Self-organize to achieve a complex task (how? which tasks?)decentralized decision-making; negotiation
Be invoked by LLM skills(new: the "person" in Hewitt's citadels is now often an LLM)
  • Hewitt also held that there is no computer-only solution: people are part of the system. That suggests Jido's sweet spot is work where agents act alongside people, not in place of them.

Where we think the sweet spot is

  • Use cases now popular in general-purpose assistants such as Hermes Agent and OpenClaw look like a natural fit for Jido agents:
    • Customer service: triage across email, web and chat, then route and track to resolution.
    • Fraud detection: many small watchers, each flagging a pattern, with escalation to a person.
    • Correspondence: drafting, follow-ups and reminders over long periods.
    • Scheduled, unattended work: daily reports, weekly audits, monitoring.
    • Document pipelines: invoices, categorization, extraction.
    • Research: delegated, multi-step gathering and synthesis.
  • What these share: they run for a long time, they are event-driven, they need fault isolation, and a person stays in the loop. OTP is good at all four.
Hypothesis 2

Jido's strongest domains are long-running, event-driven, people-in-the-loop business processes. The open-systems properties above are what set Jido apart from single-process agent frameworks.

3The potential fit between Jido and Composer

  • Jido apps have a lot of setup: agents, actions, signal routes, plugins, AI providers, persistence, and a LiveView front end.
  • A Jido cookbook would turn that setup into recipes a developer can run, and a coding agent can discover and run too.
  • Composer works at development time. It gets you to a running Jido app; it does not manage agents once they are running.

What it might look like

$ mix igniter.new my_app --install composer_jido composer_ash composer_phoenix
$ cd my_app
$ mix composer.dashboard

mix composer.dashboard (not built yet) starts a local web server and opens a dashboard in the browser:

  • Main panel: an installation graph like the Ash HQ installer, showing Jido recipes and the steps they pull in. The graph highlights the recipes that the chat suggests.
  • Sidebar: an LLM chat titled "Describe your Jido application".
Hypothesis 3

Setup friction is a real barrier to Jido adoption, and a guided "describe your app, get a running skeleton" flow would lower it.

Cookbook contents (first cut)

Recipes from the use cases in section 2:

GroupExample recipes
cs/intake, routing, metrics, sentiment
fraud/watchers, scoring, escalation
correspondence/drafting, follow_up, reminders
ops/scheduled_reports, audits, monitoring

Shared steps: add Jido, configure an AI provider, add persistence, add a LiveView agent console, and add test scaffolding for agents.

Phases

  1. Conversation (today): test the hypotheses.
  2. Prototype: a composer_jido cookbook with a few core/ recipes, to prove that the examples can be generated, not just copied.
  3. Use cases: one complete use-case recipe (customer service), end to end.
  4. Dashboard: mix composer.dashboard with the graph and chat.
  5. Ownership: decide whether the cookbook stays in the Composer project, moves to the Jido project, or is shared.
Hypothesis 4

The Jido examples can be turned into recipes with modest effort, and doing so would help keep the examples and the framework in step.

5Discussion: feedback and direction

Understanding

  • Does the Composer concept make sense? What was unclear?
  • Is "cookbook / recipe / step" the right vocabulary?

Problem

  • What are Jido's core challenges right now: developer adoption, end-user adoption, revenue, visibility?
  • Where do new Jido developers get stuck first?
  • What Jido problems might a Jido cookbook solve?

Fit and overlap

  • Does Composer duplicate functionality you plan to bundle into Jido (for example, Jido's own Igniter installers or generators)?
  • How close is our read of "Why Jido" and of Jido's sweet spot? Which use cases would you add or drop?

Risks

  • What problems do you see with the Composer concept?
  • Would generated Jido code go stale as Jido evolves? Who keeps it current?

Ownership and direction

  • Would you, in concept, support a composer_jido cookbook authored and maintained by the Composer project?
  • Would you, in concept, support a Jido cookbook authored and maintained by the Jido project?
