Composer LLM Benchmarks

In the age of LLM supremacy, is Composer helpful, or a misguided dead end?

October 2026 · Andy Leak · Copyright © 2026 by Andy Leak - All Rights Reserved

The question

Is Composer even helpful now that we live in a world where LLMs are ascendant?

  • You read about people who have their coding agent compile direct to assembler. You read that coding languages and frameworks just get in the way.
  • Composer introduces another layer of code, another artifact to maintain. In the age of LLM supremacy, is Composer a misguided dead end?

Hypothesis

Composer is a framework for assembling applications. Frameworks will still be useful in the age of LLMs, because:

  • frameworks give constraints and affordances that are useful to LLMs
  • frameworks give a standard vocabulary for humans to tell LLMs what they want
Hypothesis

LLMs are more useful when they are given direction. Tools like AGENTS.md, usage_rules and skills have proven to be effective. Composer is another way to give direction to an LLM, and it will prove useful in the age of LLMs.

Three types of user

Over time, we want to test this theory with benchmarks from the perspective of three types of user:

The AiChat End UserProbably non-technical. Someone who just wants to assemble an application with the aid of an LLM.
The Casual DeveloperAn experienced coder who can read Elixir. Builds app skeletons, then finds errors and goes into the skeleton to fix them.
The Cookbook Power DeveloperAn obsessive Composer developer, who drinks the Composer kool-aid and architects cookbooks.

Part 1 · Existential assessment

1First, fix the framing

Assessment dated 2026-10-21. Related: 261021_EaseOfUse.md (the agent-task harness proposed there is the harness this document needs), 261020_StepWiseCommits.md, 261012_Menus.md (--json output for agents), 261001_Overview.md.

"LLM vs. LLM-plus-Composer" is the wrong comparison, and it flatters Composer. Nobody serious uses a bare LLM to set up a Phoenix app in 2026. The real competitor is:

LLM + phx.new + mix igniter.install + usage_rules + a few skills

That baseline already has frameworks, generators, AST-aware installers and written-down know-how. Composer has to beat that, and the thing it most directly competes with is the skill: a markdown file that says "to add Oban, do these five things." A skill is a recipe written in English. It costs almost nothing to write, needs no framework, no Igniter knowledge and no CI, and an LLM adapts it on the fly when the target app looks a bit different.

The real question

Is a recipe better than a skill?

The "compile straight to assembler" crowd is a distraction. Frameworks are not going away: LLMs are trained on framework code, and both LLMs and humans review and extend abstractions far better than raw output. The hypothesis holds for Phoenix and Ash. But "frameworks survive" does not imply that a meta-layer above frameworks survives. Composer needs its own argument.

2The case against Composer

Steelmanned, without holding back.

  1. It optimizes the cheapest hour of an app's life. Setup happens once. An app lives for years, and LLMs help across all of them. Composer helps with the first hour, which is also the most well-trodden, best-documented, most-represented-in-training-data part of building an app. That's where LLMs are already strongest.
  2. Recipes fail hard; LLMs fail soft. When upstream changes (Phoenix 1.8 scopes, Tailwind 4, daisyUI 5), a recipe breaks and stays broken until a maintainer fixes it. An LLM reads the error, reads the new docs, and adapts. A stale recipe can be worse than no recipe, because it confidently produces a broken app. 261021_EaseOfUse.md already flags cookbook maintenance as the red flag; in the LLM comparison it's the central weakness.
  3. Real apps leave the recipe within an hour. Recipes cover the common path. The long tail (this auth provider, that odd deploy target) is where the work is, and the LLM handles it either way. If Composer covers 80% of setup and setup is 2% of the work, the ceiling on its value is low.
  4. Skills capture the same knowledge at a fraction of the cost. Writing a step needs Igniter, which is the steep part of the SuperDev curve. Writing a skill needs English. If an LLM following a skill reaches the same result at similar cost, Composer is a more expensive way to store the same knowledge.
  5. The Neophyte is not going to choose Elixir. A non-technical user who wants an app goes to a hosted AI app builder and gets a running URL. They don't care what language it's in. The Neophyte story only works if someone else (a CasualDev, an agency, composable.tech) has already chosen Elixir for them.
  6. It depends on network effects in a small ecosystem. A cookbook ecosystem needs many authors. Elixir is a small community, and authors now have a cheaper option (skills) for sharing the same know-how.
  7. Another artifact for the LLM to learn. Composer's DSL is not in any model's training data. Every agent session pays tokens to learn it from usage_rules before it pays off.

3The case for Composer

  1. Determinism. Same recipe, same flags, same result, every time. An LLM run varies from run to run and from model version to model version. For a team ("all our services start the same way"), for audit, for support ("which version of the auth setup do you have?"), that's worth a lot, and no skill provides it.
  2. Cost and speed. A recipe runs in seconds for zero tokens. An agent setting up auth + Oban + Tailwind + daisyUI + a dashboard takes dozens of turns, minutes, real money, and sometimes a human rescue. At one app, who cares. At a thousand apps (a marketplace, an agency, CI), it matters.
  3. Selection is easier than generation. With Composer as a tool, the agent's job shrinks from "write and edit 3,000 lines" to "pick six steps and set two flags." Choosing from a catalog with requires/conflicts checks is a far easier task for an LLM than open-ended generation, and its mistakes are caught before anything runs (composer.menu.check).
  4. Smaller review surface. A human reviews an eight-line recipe, not a 3,000-line diff. With step-wise commits, each change is attributed to a named, tested step. This is the strongest argument for the CasualDev: you can trust what you didn't read, because someone tested it.
  5. Tested knowledge, not remembered knowledge. LLMs write Elixir well at the language level; where they slip is current library versions and the integration seams between packages (config keys that moved, installer flags that changed, CSS that clashes). Those are exactly what a recipe pins down and a golden-app test verifies. A skill is advice; a green recipe is proof.
  6. Igniter edits are structural and idempotent. AST-aware, composable edits are more reliable than an LLM's text edits on a config file it is seeing for the first time.

4Where the two sides meet

Read the lists side by side and one pattern stands out:

Every "against" point

is about Composer as a human-facing tool that competes with the LLM.

Every "for" point

is about Composer as a deterministic, tested execution layer that the LLM calls.

That suggests the role Composer should aim for:

The LLM decides. Composer executes. Tests verify.

In that picture:

  • A recipe is a cached, verified LLM plan. The first time, an LLM works out how to add Oban properly. Composer turns that into a step that is tested, versioned and reusable, and nobody (human or agent) pays to work it out again.
  • LLMs write the steps. The Igniter barrier for SuperDevs mostly goes away if an agent writes the step and composer.try (from EaseOfUse) proves it. The SuperDev reviews.
  • LLMs repair the steps. Point 2 against ("recipes fail hard") is answered if nightly golden-app tests catch drift and an agent opens the fix. Then recipes fail hard in CI, not in the user's hands.
  • Composer's primary user is an agent. The human-facing parts (TUI, menus, web UI) still matter, but the --json interfaces, the step metadata (summary, facets, requires) and an MCP server are the main interface. Search and discovery "by humans and agents" (README) should read "by agents, and humans".

5Conclusion

Verdict

Composer is not a dead end, but it is a dead end in the shape of "a better generator for humans." The pure human-tool version loses to LLM + skills within a couple of years: the LLM gets better every quarter, and the cookbooks rot unless someone pays to maintain them.

It is worth pursuing as the execution layer for agents, where determinism, cost, verified integration knowledge and small review surfaces are real advantages that LLMs don't remove and skills don't provide.

The hypothesis is right, with one adjustment: Composer is not mainly a way to give direction to an LLM (that's what skills and usage_rules do, more cheaply). It is a way to give an LLM reliable, tested actions to take.

Two claims to test early

Confidence is moderate, and it rests on two claims:

  1. On covered tasks, LLM + Composer beats LLM + skills on success rate and on cost/variance by a clear margin, not a few percent.
  2. A tested recipe stays correct longer, or is cheaper to repair, than a skill when upstream versions move.
  • If (1) fails, Composer's value shrinks to determinism alone, which helps teams and marketplaces but isn't enough to carry a cookbook ecosystem.
  • If (2) fails, the maintenance burden makes the whole thing a losing trade.
  • Either result would be a reason to stop or pivot (for example: ship the cookbook knowledge as skills + Igniter installers, and drop the recipe layer). Both are cheap to test, so test them before building more surface area.

Part 2 · Benchmark approach

6The experimental design

For each type of user: would an LLM plus Composer be more helpful than an LLM alone? The design below is shared by all three users.

Arms

Every task runs under at least three conditions. Arm B is the one that matters; without it the benchmark only proves that context helps an LLM, which nobody doubts.

ArmConditionWhat the agent has
ABare LLMmix, phx.new, web docs
BLLM + skills (the real competitor)A + igniter.install, usage_rules, and a skill per feature with the same know-how as the recipes
CLLM + ComposerA + Composer as a tool (--json / MCP), its usage_rules, the cookbooks
DComposer alone (CasualDev only)No LLM: a human runs the recipe

To keep B fair, write the skills from the same source as the steps: same packages, same versions, same config. Ideally, have an agent turn each step into a skill, then have a human check it.

Task tiers

Composer should win on covered tasks. The real question is whether it hurts on everything else.

TierExampleWhy it's there
Covered"Phoenix app with auth, Oban, daisyUI, admin dashboard"Composer's home ground
PartialCovered task + "add Stripe webhooks"Does the recipe help or get in the way after it?
UncoveredSomething no recipe touchesDoes Composer's presence cost tokens or confuse?
Follow-onDay 2: "add a feature" to the app built in an earlier tierAre Composer-built apps easier to extend?
DriftA covered task, pinned to upstream versions newer than the model's cutoffTested recipe vs. the LLM's memory vs. a skill
  • The drift tier is where Composer's "tested knowledge" claim either holds or doesn't.
  • The follow-on tier answers the "cheapest hour" objection: if Composer only helps in the first hour, it shows up here as no difference.

Scoring

Automated, from the golden-app checks in EaseOfUse:

  • Success: compile --warnings-as-errors, generated tests pass, app boots, plus hidden acceptance probes per task (a scripted HTTP check or a Wallaby script: can I register, log in, enqueue a job, see the dashboard?). The agent never sees the probes.
  • Cost: tokens, dollars, turns, wall-clock time.
  • Variance: run each task/arm N ≥ 5 times. Report success rate and the spread of the result (diff size, files touched). Determinism is one of Composer's claims, so measure it.
  • Quality: credo, sobelow, mix format --check-formatted, diff size.
  • Human interventions: count of times a human had to step in (for the human-in-the-loop personas).

Hygiene

  • Pin the model and the harness version. Re-baseline every arm when either changes, or the graph measures the model instead of Composer.
  • Run at least two model families, since Composer's value should not depend on one vendor's quirks.
  • Freeze the task list; add new tasks as a new suite version, never by editing old ones.

7The AiChat End User

Would LLM + Composer help?

Probably yes on covered tasks: higher success rate, much lower cost, much lower variance. The user can't read code, so a broken app is a dead end for them, and reliability is the whole product. Composer's selection-over-generation shape is a good fit: the agent maps "I want people to log in and pay me" onto menu picks, which composer.menu.check validates before anything runs.

But be honest about the ceiling: this user doesn't care that the app is Elixir, and they need hosting, not a repo. This persona matters only through a front end (composer_web, composable.tech) that someone else builds.

Benchmarks

  • Automated (now): an agent plays the user. It gets a plain-language brief ("a booking site for my yoga studio, members log in, I can see who booked") and may not read or edit code. Arms A/B/C. Score on the hidden acceptance probes.
  • Simulated user (now): a second LLM plays a non-technical user with a hidden spec, and answers the building agent's questions vaguely, the way a real user would. Measures how well each arm turns fuzzy requirements into a working app, and how many clarifying turns it needs.
  • Human trial (later, once a front end exists): 5 to 8 non-technical participants, each given a brief, using a chat UI wired to arm B or C (between-subjects; they can't do both without learning the task). Record completion, time, number of "it's broken" moments, and a short SUS questionnaire. Until there's a front end, a Wizard-of-Oz version works: a facilitator relays the chat.

8The Casual Developer

Would LLM + Composer help?

This is Composer's strongest persona, and the one to benchmark first. The CasualDev can read code but doesn't want to. The benefits that matter to him:

  • Trust without reading: a recipe of named, tested steps, each in its own commit, versus a large LLM diff he has to review line by line.
  • Fewer fix-up loops: fewer "it compiles but the CSS is broken" moments.
  • Knowing what he has: he can say "this app is core:saas/default plus two steps" and look each one up.

The risk is the partial tier: if the recipe gets him 80% of the way and then the LLM struggles with Composer-shaped code, he's no better off.

Benchmarks

  • Automated: the same agent harness, but the agent may read and edit the generated code (that's the CasualDev's workflow). All tiers. The partial and follow-on tiers matter most here.
  • Human trial, crossover design: 5 to 8 Elixir developers, two comparable task lists (say, SaaS starter and internal admin tool). Each developer does one list with arm B and one with arm C, with order and pairing counterbalanced. Measure time to a green app (acceptance probes), interventions, and defects found by the probes afterwards.
  • Comprehension check: after each task, five questions about the app they just built ("where is the Oban config?", "what does the auth flow do on a failed login?"). If Composer users can't answer them, "trust without reading" has turned into "doesn't know his own app", which is a real cost.
  • Review cost: give a second developer the result of each arm and time how long a confident review takes. This is the cleanest test of the "smaller review surface" claim.

9The Cookbook Power Developer

Would LLM + Composer help?

It's a different question for this persona. He isn't building apps; he's packaging know-how. The comparison is:

Know-how as a step (Igniter code + tests) vs. know-how as a skill (markdown)

A step costs more to write. The bet is that it pays back through reuse (cheaper and more reliable for every app built after) and durability (easier to keep correct). With an LLM writing the step and composer.try checking it, the authoring cost gap may be small.

Benchmarks

  • Authoring: tasks like "package this blog post as a step" and "package it as a skill." An agent does both, with a human reviewing; record time, tokens and review time to a result that passes golden-app tests (step) or passes the same acceptance probes when an agent follows it (skill).
  • Payback: run each artifact N times through the end-user harness. Plot cumulative cost (authoring + per-use tokens + failures) against number of uses. Where the lines cross is the break-even point. If a step only pays off after 500 uses, most steps never will, and the cookbook model is in trouble.
  • Durability (the most important long-run benchmark): keep a fixed set of steps and their twin skills. Every month, or on every upstream release, run both against the latest versions. Record which stays green, and the cost (human minutes + agent tokens) to bring each back to green. This answers claim (2) from the conclusion, and it needs months of data, so start it first.
  • Repair by agent: break a recipe on purpose by bumping an upstream version, then time an agent fixing it with composer.try as its loop. If agents can do this unattended, the maintenance concern mostly goes away.

10What to do first

A small first experiment, roughly a week of work, that tests both claims:

  1. Pick three covered tasks from composer_lab recipes that already work.
  2. Write the twin skills for them.
  3. Build the minimal harness: scratch app, agent run, acceptance probes, one JSON line per run (as in EaseOfUse).
  4. Run arms A, B and C, five runs each, one pinned model.
  5. Start the monthly durability job on those three steps and skills.
Decision rule

Agreed before looking at the results: if arm C doesn't beat arm B by a clear margin on success rate or cost on covered tasks (say, +20 points of success, or half the cost at equal success), stop and rethink the recipe layer before building more of it.

11Open questions

Harness location

  • Where does the harness live? Same question as EaseOfUse; it should be one harness for both documents.

Budget

  • 3 tasks × 3 arms × 5 runs × 2 models is 90 agent runs. Fine for the first experiment; the full tier matrix needs a run budget.

Twin skills

  • Who writes them? If a Composer enthusiast writes them, arm B is at risk of being a weak strawman. An outsider, or an agent with a fixed prompt, keeps it honest.

Publishing

  • Should we publish the results? A public benchmark (on elixir-composer.dev), including the cases where Composer loses, is good marketing and keeps the project honest.
